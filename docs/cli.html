The CLI

The command line: the loop an author lives in.

Two kinds of verb. Seven of them — schema, vocab, model, tokens, data, validate and explain — need no weights. They say what exists, what a document means and whether it would compile, in seconds on a laptop, against a model that may only ever run on someone else's GPU. run is the eighth, and the only one that loads the weights.

Every verb takes --json, so an agent parses instead of scraping. Every verb writes to stdout and nothing else; only run touches the disk.

At a glance #

The loop is check, read, run. All three commands below take the same document, the smallest interchange in the repository: four rows, one swap at the last token of layer 0 of a tiny random-weight Llama. Documents is the page for what is in it.

$ uv run causalab-mini validate documents/v2/patching.json
ok: documents/v2/patching.json is a valid plan-shaped document, 1 step

$ uv run causalab-mini explain documents/v2/patching.json
<root>: Plan
  score: Observe  metrics=['iia/match', 'logit_diff/logit_diff']  saves=['iia.json', 'logit_diff.json']
      forward 'original' on 'counterfactual'  (4 rows x 11 tokens)
        read  'v_cf' at block_output[0] pos={index:-1} via 'identity'
      forward 'patched' on 'base'  (4 rows x 11 tokens)
        write 'patch' at block_output[0] pos={index:-1} swap(v_cf) via 'identity'
        read  'logits' at lm_head pos={index:-1} via 'identity'

$ uv run causalab-mini run documents/v2/patching.json --device-map cpu --out out/cli/patch
out/cli/patch/document.json
out/cli/patch/run.json
out/cli/patch/iia.json
out/cli/patch/logit_diff.json

The whole run took 7.9 s on twelve CPU cores, model load included. run prints the paths it wrote, in the order it wrote them, and that is its entire output.

The options are few. model and tokens take --revision (default main); model also takes --dtype, one of fp32 and bf16. data, validate, explain and run take --data-root, which defaults to documents/data — a relative path, so these commands expect to be run from the repository root.

the cost is the import

Every verb pays about 6.3 s starting up, because importing causalab_mini.cli imports torch and nnsight. That is the whole cost of schema, vocab and validate: measured here, import causalab_mini.cli alone is 6.27 s and validate is 6.23 s. Budget for it in a loop; do not read it as the work.

$ uv run causalab-mini schema | jq -r '."$defs" | keys | join(", ")'

the verb cannot ask for eager attention

model builds its model spec from --dtype and --revision only, so it always asks for the library default (sdpa) and attention_scores and attention_probs always report --. Checking a document: one question, printed or not #

validate and explain do the same work. Both load the model as a meta-device shell — the config, the module tree, the tokenizer, no weights — resolve every address, tokenize every prompt and compile the plan. explain prints it; validate says whether it compiled, and in which of the two formats the file is written. Both take --data-root and --engine, and both use them.

$ uv run causalab-mini validate documents/v2/patching.json
ok: documents/v2/patching.json is a valid plan-shaped document, 1 step

$ uv run causalab-mini validate documents/pos_sweep_cpu.json
ok: documents/pos_sweep_cpu.json is a valid protocol document, 3 steps

So a misspelled component fails at validate: a component name is a question about a model, and this verb has one.

$ uv run causalab-mini validate out/cli/typo.json
AddressError: component 'block_ouput' has no address here, and this model's internals have no accessor of that name either. Mini's are ['attention_input_norm', 'attention_key', 'attention_output', 'attention_premix', 'attention_probs', 'attention_query', 'attention_scores', 'attention_z', 'block_input', 'block_mid', 'block_output', 'embeddings', 'input_ids', 'lm_head', 'ln_final', 'logits', 'mlp_activation', 'mlp_input', 'mlp_input_norm', 'mlp_neuron_output', 'mlp_output']; add one to a model with RenameConfig(addresses={...})

A refusal is a message on stderr and exit 1, not a traceback. The entry point catches this package's own error types by name — PlanError, DocumentError, AddressError, TokenError, LocateError, DataError, EngineError, pydantic's ValidationError and nnterp's RenamingError — and prints what they say. Nothing generic is caught, so a missing file is still a traceback. --traceback, before the verb like --json, restores the whole thing.

One exception, and it is a run through --engine ndif. nnsight flattens whatever the server raised into RemoteError, which is not one of the nine, so a remote refusal comes back as a traceback — 45 lines of it, ending in the same text and the same exit code. When the server refuses has the transcript and what the fix would be.

There is no --dry-run, no --verbose and no --force. explain is the dry run; the output is the paths; and nothing is ever refused for already existing — see the caution under the output layout.

--engine: three runtimes, one plan #

--engineclassweightswhere it runs
nnterpNNterpEngineloaded here, under --device-mapthis process, in one nnsight session
ndifNNterpEngine, dispatch=Falsenone locally — a meta shellan NDIF server, which has the weights
hooksHooksEngineloaded herethis process, one register_forward_hook per tap

Compiling is a weightless shell for all three, so explain prints the same plan whichever engine you name — for documents/v2/patching.json the three outputs are identical here. What differs is which addresses a runtime accepts, and where the forward happens.

The hooks engine is a plain HuggingFace model with a forward hook on each module a tap names. A hook fires at a module's boundary and sees nothing inside it, so the four interior components — the query, the key, the scores and the attention output before the out-projection — are refused by name rather than approximated. Everything else it reaches, including logits: a hook is handed the module's whole value and nnterp's row says where the tensor is inside it, which for the model's own output is the logits field. model --engine hooks is how you find out without running anything:

$ uv run causalab-mini model hf-internal-testing/tiny-random-LlamaForCausalLM --engine hooks
hf-internal-testing/tiny-random-LlamaForCausalLM via hooks: 2 layers, sdpa attention, padding_side=left
  attention_query    --   component 'attention_query' is an interior — one argument of one call inside a module's forward — and a forward hook only sees the module's boundary. It is addressed through nnsight's `.source`, which has no hooks equivalent; run this document on the nnterp engine.
…
  block_output       ok   width=16
  ln_final           ok   width=16
  lm_head            ok   width=32000
  logits             ok   width=32000

Everything a hook can reach, it reaches identically. Running documents/v2/patching.json on both engines here produced byte-identical iia.json and logit_diff.json; the run took 6.7 s on hooks against 7.9 s on nnterp. The two run.json files differ in the engine name, and in that only the nnterp one has a served_dtype: that field is read off the model inside the session, and only the nnterp engine has one.

There is no flag that runs hooks remotely, and the engine refuses one by name if it is asked: a hook is a Python callable registered on a module object in this process, and NDIF runs the model in another one, so there is nothing here to ship.

--engine ndif loads the same nnterp shell with dispatch=False — module tree and tokenizer, no parameters — and executes the compiled plan inside model.session(remote=True). --device-map is not passed at all. The model key must name a model the server hosts, and the run record says "remote": true. Remote & NDIF is the page for it.

this machine cannot finish a remote run

Run here, --engine ndif reaches the service — the job is received, queued, dispatched and started — and then comes back with RemoteError: Your request payload could not be read (AttributeError: Can't get attribute '_replace' on <module 'dataclasses' from '/usr/local/lib/python3.12/dataclasses.py'>). The server's Python is 3.12 and this client's is 3.13. Everything on this page was therefore run locally, and what --engine ndif does is read off the code rather than demonstrated.

--batch-size #

A window of rows is a whole small pass: the same forwards in the same order over a slice of the rows, with each published value sliced the same way so a write still meets the operand of its own row. What the windows read is concatenated back in row order, and everything after that — metrics, eligibility, outputs, saves — sees one pass. With no --batch-size there is one window, which is the pass exactly as compiled.

It is a property of the run and not of the experiment, which is why it is absent from document.json and present in run.json. It is not free of consequence: a GEMM over fewer rows rounds differently. The four rows of documents/v2/patching.json, run whole, in twos and in threes:

--batch-sizelogit_diff, row 3
absent-0.19330616295337677
2-0.19330616295337677
3-0.19330619275569916

At 2 both tables came out byte-identical to the unbatched ones here; at 3 — which does not divide the four rows — the last digits of one row move. Do not count on either: FINDINGS.md §18 records the same comparison across patching, windows, the logit lens, generation, heads, neurons, a ragged harvest and a DAS fit, at batch sizes 1 and 3, and what it pins is agreement to 1e-6, not bit-equality.

What it does not do is bound the memory of a fit's update. The loss is the mean over the concatenated rows, so every window's graph is alive until the backward; a fit's memory knob is its pairs. It does bound the held-out pass, which runs under no_grad.

What lands on disk #

The plan's save manifest, and nothing else. Every file that leaves a run is a saves entry in the document, plus the document.json every plan's directory carries and the run.json the root carries. One document with one plan writes straight into --out:

out/cli/patch/
├── document.json      the experiment, verbatim, as it was given
├── run.json           what ran it
├── iia.json           a metric table
└── logit_diff.json

A nested plan writes below its parent in a directory named by its step name, so a plan's path in the tree is its path on disk. A sweep is exactly that: one root plan whose children are one plan per point, named for the field and the value it took.

$ uv run causalab-mini run documents/pos_sweep_cpu.json --device-map cpu --out out/cli/sweep
out/cli/sweep/document.json
out/cli/sweep/run.json
out/cli/sweep/pos=-1/document.json
out/cli/sweep/pos=-1/iia.json
out/cli/sweep/pos=-1/logit_diff.json
out/cli/sweep/pos=-2/document.json
out/cli/sweep/pos=-2/iia.json
out/cli/sweep/pos=-2/logit_diff.json
out/cli/sweep/pos=-3/document.json
out/cli/sweep/pos=-3/iia.json
out/cli/sweep/pos=-3/logit_diff.json

The directory name is the swept field's own name and the value it took, or the axis name when the sweep is a named one. The root's document.json is the document you wrote, sweep wrappers and all — its pos is still {"sweep": [-1, -2, -3]}. Each point's document.json is that point: the wrapper replaced by one value. So each point has its own digest, and each point's metric rows say which one produced them.

run.json is written once, on the root, because the engine records what ran on the plan it was handed.

A step that trains a featurizer writes it as a safetensors bundle alongside the tables, with its identity stamped into the header — the thing a later document's file_path load checks before trusting the rotation:

nothing is cleaned

--out is created if it is missing and written into if it is not. Files the run produces are overwritten; files from an earlier run that this one does not produce are left where they are. A directory reused across two different documents will hold both, with only document.json and the rows' produced_by to say so. Give each run its own --out.

columnwhat it is

--json, for agents #

Each verb returns one dictionary with a text key. --json prints the dictionary; without it, only text is printed. So the human output and the machine output are the same run, never two code paths that can disagree.

--json is on the top-level parser, so it goes before the verb:

$ uv run causalab-mini --json validate documents/v2/patching.json
{
 "text": "ok: documents/v2/patching.json is a valid plan-shaped document",

 "format": "plan-shaped"
}

$ uv run causalab-mini validate documents/v2/patching.json --json
usage: causalab-mini [-h] [--json]
                     {schema,vocab,model,tokens,data,validate,explain,run} ...
causalab-mini: error: unrecognized arguments: --json

Exit codes, and what an error looks like #

codewhen
0the verb ran
1an uncaught exception. The traceback is the error message
2argparse: no verb, an unknown verb, an invalid --engine, --json after the verb

There is no error handling in the command line at all: a refusal is an exception, and it arrives with its stack. That is deliberate — the frames say which of the compiler, the address layer, the walk or the engine refused — but it means the sentence you want is the last line. Three real ones, each trimmed to its first line and its last, which is where the sentence is. This one exits 1:

$ uv run causalab-mini run documents/attention_query_cpu.json --engine hooks --device-map cpu --out out/cli/q-hooks
Traceback (most recent call last):
…
causalab_mini.address.AddressError: component 'attention_query' is an interior — one argument of one call inside a module's forward — and a forward hook only sees the module's boundary. It is addressed through nnsight's `.source`, which has no hooks equivalent; run this document on the nnterp engine.

A document that does not match the schema fails in pydantic, which names the field by its path:

$ uv run causalab-mini validate out/cli/badmetric.json

interventions.patching.metrics.iia.match.expected
  Field required [type=missing, input_value={'kind': 'match', 'of': '...form': 'space_prefixed'}, input_type=dict]
    For further information visit https://errors.pydantic.dev/2.13/v/missing

And a refusal that only the run can make, because only the run has the rows. A read may skip a row it cannot place; a write may not:

$ uv run causalab-mini run documents/v2/entity_patch.json --data-root out/cli/neptune-data --device-map cpu --out out/cli/neptune
Traceback (most recent call last):
…
causalab_mini.plan.plan.PlanError: write 'patch' has nothing to write on row(s) {1: 'alignment_missing'}. A read may skip a row; a write may not — writing nothing somewhere is not an intervention, and the row would score as if one had happened. `alignment_ambiguous` is a value that is in the prompt more than once, and scoping the anchor is what makes it one

The same hole on a read is not an error. It comes home as a row of the table with eligible: false, positions: [] and reason: "alignment_missing" — which is the case tests/test_eligibility.py pins. Whether a row the run cannot place stops the run or is reported depends on whether something was to be written there, not on the data.
