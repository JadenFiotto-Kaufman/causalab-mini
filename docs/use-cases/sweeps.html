Use case

Sweeps

One document that is several experiments: the wrapper, the cross product, named axes, and one directory per point.

{"sweep": [a, b, c]} at a field means the document is three points: the same experiment three times, differing in that one field. A swept document compiles to a root plan whose children are one plan per point, and a plan's path in the tree is its path on disk.

A sweep is lowered on the raw JSON, before anything is compiled. The wrapper is replaced by each of its values in turn and each resulting document is compiled on its own, so a point is an ordinary document in every way — its own addresses, its own tokenization, its own digest — and nothing downstream of the compiler knows a sweep happened.

The wrapper

A wrapper is an object whose keys are sweep and, optionally, as — nothing else. That is how the lowering tells a wrapper from an ordinary object with a field called sweep, and it is why a wrapper holds one list and not several fields.

spellingvalues
{"sweep": [-1, -2, -3]}the literal list
{"sweep": {"range": [0, 16]}}0, 1, … 15
{"sweep": {"range": [0, 16, 4]}}0, 4, 8, 12
{"sweep": [-4, -1], "as": "pos"}a named axis — see below

A range is [start, stop] or [start, stop, step], in integers, and means what Python's range means — half-open, so [0, 16] is a 16-layer model's every layer and not seventeen of them.

Where a point lands, and what it is called

A point's name is the swept field's own name — the last string key on the path to the wrapper — and the value it took. That name is the plan's name in the tree and its directory on disk:

The root carries the document you wrote and the run record; each point carries the document it became. Nothing on disk is named by position in a list, so adding a value to a sweep does not rename anyone else's results.

A one-element list collapses in the name

Several of the things worth sweeping are lists that happen to hold one element: a layer band, a single head, one SAE latent. In a point's name a one-element list is written as its element; anything longer is written as compact JSON. Three documents, three shapes of value:

heads: {"sweep": [[0], [1], [2], [3]]} gives heads=0, because a site's heads field is a list and each point wants one of them. units sweeps lists of four and keeps the list. Only the name collapses — the document at each point holds the list it was given.

Two axes

Several swept fields are their cross product, one point per combination, labelled in the order the fields appear in the document. documents/real/weekdays_layer_sweep.json has two: a range over the 16 layers of a site, and a two-value sweep of the position — which is why its points are called layers=12,pos=-1.

Three wrappers are in that document, in three places. The site's layers holds {"sweep": {"range": [0, 16]}}; the read v_cf and the write patch each hold {"sweep": [-4, -1], "as": "pos"} as their position. The whole document is on Layer sweep.

three wrappers, two axes

The document holds three wrappers. Two of them carry "as": "pos", so they are one coordinate: the read's position and the write's move together. That is 16 × 2 = 32 points. Swept separately they would be 16 × 2 × 2 = 64, and 32 of those would read one place and write another — a patch of the counterfactual's last token into the base's day token, which is not an experiment anyone wrote.

Every field on a named axis needs a value per point, and a mismatch is refused naming both places:

$ uv run causalab-mini validate swept_mismatch.json
Traceback (most recent call last):
  …
causalab_mini.plan.sweep.SweepError: interventions.patching.writes.patch.pos: axis 'pos' has 2 values at interventions.patching.reads.v_cf.pos and 3 here; fields that move together need a value each per point

What that says about the model is on Layer sweep. What it says about sweeps is that a grid of experiments is a grid of directories, and the directory names are the coordinates.

Asking a swept run for a result

Result names come from the document, so they are unique within a plan and repeated across a sweep's points. Asking the root for one is an error, not a first match:

>>> root.result("iia")
causalab_mini.plan.plan.PlanError: result 'iia': 3 in this plan. Results here: ['iia', 'logit_diff']

>>> float(root.steps["pos=-2"].result("iia").mean())
0.0

Naming the point is what disambiguates, and the point's name is the same string as its directory. all_results() refuses on a sweep for the same reason; ask a point instead.

these numbers mean nothing

pos_sweep_cpu.json runs on hf-internal-testing/tiny-random-LlamaForCausalLM, whose weights are random. iia is 0.00 at all three positions and the logit differences are within ±0.2 of zero. It is a document about the plan tree, not about a model.

What is refused

documentmessage
a swept model or header model.dtype is swept; a sweep may not change the model or the header — those are the identity of the run, not a coordinate in it
an empty sweep sites.target.layers.0: a sweep of nothing
a range that is not one a range is [start, stop] or [start, stop, step] in integers, got [0, 16, 0]
a named axis of two lengths axis 'pos' has 2 values at … and 3 here; fields that move together need a value each per point

The first one is the load-bearing refusal: the engine loads the model once and every point runs against it, so a point may not ask for a different one. That is also why the CLI reads the first point to find out what to load.

Below that, Spec and Document each describe one point, so either of them meeting a wrapper means the lowering did not run. Both front ends check for it rather than letting a {"sweep": …} object be validated as whatever field it is sitting on.

The protocol allows more here than mini implements — at_once, cohorts, swept parameter bundles. Those are refused by name rather than loaded and ignored.
