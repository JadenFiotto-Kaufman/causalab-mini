Use case

Generation

A forward that keeps going: decode: N, positions along what the model said, and a write that fires at every step.

decode: N on an intervention makes every forward of that intervention a prefill plus N greedy steps instead of one pass. With it a read or a write may name the continuation frame — {"frame": "generated", …} — a position along what this row generated, rather than along the prompt it was given.

Two documents in the corpus use it, and between them they use the two halves of the frame. generate_probe.json reads at a decode step, swept, so each step is a point of the sweep. generated_answer.json reads at a cut of the finished continuation — the last token of a word the model said — which is a place a row may not have, and the run reports which rows had it.

Three points, one per decode step. decode=3 is on both forwards, because it is a property of the intervention and not of one read. The write is in the prompt frame at pos={index:-1}, so it happens once, at the prefill; the read is @step 2, two greedy tokens later.

The decode is a bound, not a stop #

A decoding forward is one generate trace with max_new_tokens and min_new_tokens both set to decode, and sampling off. Every row produces exactly N tokens and the batch stays rectangular, which is what lets a step be a position at all: step 2 is step 2 on every row.

EOS is held off

Forcing the bound means a row that would have stopped does not. That is not thrown away: the continuation's frame is cut at the row's first stop token, the stop token is the last one in it, and a row that never stopped has the whole bound and no eos segment. "Did the model stop?" comes home as a reported reason on the row rather than as an exception that ends the run.

The character map the frame uses is built from the ids the decode produced, not by re-encoding the text it decoded to. A tokenizer is free to merge across a boundary the decode never saw, and then a span found in the re-encoded text would name tokens that never existed.

The two halves of the frame #

A read may name any cut of the continuation, because by the time the run scores it the whole continuation exists. A write happens during the decode, so it may only name a step the decode has already reached.

positionwhat it namesreadwrite
{"frame": "generated", "index": k}, k ≥ 0 decode step kyesyes
{"frame": "generated", "all": true} as a write, every decode step; as a read, every token of the finished continuation — which is a window, so no metric scores it directly yesyes
{"frame": "generated", "index": -1} the last token of the finished continuationyesno
{"frame": "generated", "index": -1, "scope": {"variable": "c"}} the last token of where column c's text was saidyesno
{"frame": "generated", "index": -1, "scope": {"segment": "eos"}} the row's stop tokenyesno

The bottom three are cuts of something that does not exist until the decode has finished. A read of one fires at every step and the stack is cut afterwards; a write is refused, by name:

The generated ids come home #

A decoding forward publishes one more value than a plain one: <model>.generated, the ids it produced, prompt stripped. The document saves patched.generated to a safetensors file, and it is a [4, 3] int64 tensor — four rows, three steps. Decoded, all four rows of this point are 'Handler substr energ': the weights are random, so the continuation does not depend on the prompt.

The prompt-frame write reaches those steps only through the cache — nothing writes at step 1 or step 2. Measured against the same model with no write at all, the probabilities move by up to 1.4e-07 at step 0, where the write lands, and by up to 4.6e-09 at steps 1 and 2. Small, and not zero.

Two reads, both at the head, both cuts of the finished continuation:

$ uv run causalab-mini explain documents/v2/generated_answer.json
<root>: Plan

        read  'at_said' at lm_head over 6 steps pos={generated index:-1 scope:{variable:said}} via 'identity'
        read  'at_stop' at lm_head over 6 steps pos={generated index:-1 scope:{segment:eos}} via 'identity'

over 6 steps is what a cut costs: the read cannot say which step it wants until the decode has finished, so it fires at every one, keeps a value per step, and the stack is cut against the continuation afterwards.

a cut has a size, and it is checked before the run

Keeping every step is rows × decode × width numbers, which is nothing at decode: 6 on a 16-wide site and a gigabyte at decode: 256 on a wide one. The compiler knows all three numbers before any weights are loaded and refuses above 256 MiB, naming the three ways out: name the step instead of a cut, decode fewer tokens, or score fewer rows in one pass. --batch-size is not one of them — the count is the whole pass's rows.

the second read is the EOS cut

at_stop is {"frame": "generated", "index": -1, "scope": {"segment": "eos"}} — the row's stop token. Because the decode is a bound and EOS is held off, no row here stops, so no row has an eos segment and all four resolve to alignment_missing. Nothing is saved from it; it is in the document to show that "the model never stopped" is a position that fails to resolve rather than an error.

Writing at every step: steering #

No document in documents/ writes in the continuation frame. This one was written for this page and run here; it is not part of the corpus. It reads the layer-0 residual at the prompt's last token from the un-written model, then adds it back, scaled by 4, at every decode step of a second model.

@step all is the whole difference from generate_probe, where the same site carried @step nothing at all. A tap in the prompt frame applies at step 0, the prefill; a tap at {"index": k} applies at step k; a tap at {"all": true} applies at every step, prefill included.

Where it lands is decided per step, not compiled in: past the prefill the forward sees one position, so the write goes to the last index of whatever the sequence axis has. At the prefill that is the prompt's last token, which is where v_last was read.

What is refused #

documentmessage
a generated position with decode: 0 read 'clean_logits': a generated position needs `decode` > 0
a read or write past the budget write 'push': step 5 of a 3-token decode
a write at {"index": -1} or at the eos cut a write in the continuation frame is at a step the decode has reached …
a write with a scope write 'push': a write in the continuation frame takes no scope; … is only known once the decode has finished

One more is refused a level down: {"scope": {"segment": "eos"}} in the prompt frame. eos is a run of the generated frame, and a prompt does not have one.

The other direction is refused too: a chat turn in the generated frame. eos is the one segment name a frame invents; every other one is a turn of the prompt, and a conversation names it — see chat turns.
