Use case

DBM fit

Differentiable binary masking: a learned mask over a site's units.

A DAS fit asks which directions of an activation carry the answer. A DBM fit asks which units — which coordinates of the residual stream, in the basis the model already uses. The parameter is one number per unit, and what a run keeps is a mask: this unit comes from the counterfactual, that one stays.

That makes it the same sentence as a subspace swap with "units" for "directions", and the same document with three fields changed. This page runs documents/v2/dbm.json, which sweeps the sparsity pressure, so the document is a sparsity curve.

At a glance #

The gate featurizer, in three lines:

featurize(x) = (x, 0)
inverse(f, 0, x) = m ⊙ f + (1 − m) ⊙ x

m = σ(θ / T)   while the fit is updating θ      (soft, so a gradient reaches it)
m = [θ > 0]    whenever the mask is scored      (hard, so the score is of a real mask)

The features are the activation — nothing is projected — which is why a gate needs no k. The parameter is θ, one number per unit of the site, and the two readings of it are the one piece of mode in the library.

no k, no seed, and every unit starts off

A gate masks every unit of its site, so a k on one is refused; it starts at θ = 0 rather than from a draw, so a seed on one is refused too. At θ = 0 the soft mask is ½ everywhere and the hard mask — θ > 0 — is off everywhere. An unfitted gate is a write that does nothing.

The document #

Reading it in the order the compiler does:

  • model is the tiny random-weight Llama at layer 0, whose residual stream is 16 wide — so the mask is 16 numbers and you can print it.
  • featurizers.mask is {"kind": "gate"} and nothing else. There is nothing else to say.
  • interventions.dbm is an interchange: read v_cf through the gate on the counterfactual prompt, write it through the same gate into the base run. Two metrics — ce, the cross entropy of the counterfactual's answer, and iia, which in this document is a logit_diff, the margin between the two answers.
  • steps.fit trains mask for 20 epochs, then steps.score scores the fitted mask on the training rows and steps.weights publishes θ for the save.

The three differences from a DAS fit #

The header says the only differences from documents/v2/das.json are the featurizer's kind, one objective term and the anneal. Renamings aside, that is what diff shows, plus the optimizer settings a different parameter wants:

The two new fields #

<gate>.mask in the objective #

An objective is a list of [weight, term] pairs, summed and minimized. The terms are usually metrics. A gate publishes one more under its own name: mask.mask is the soft mask, and the objective takes its mean — so a positive weight on it is L1 pressure toward keeping few units.

There is no maximize flag anywhere: the sign of the weight is the direction. [1.0, "ce"] minimizes a cross entropy; [-1.0, "logit_diff"] would maximize a margin. Here the two terms pull against each other — the cross entropy wants whatever units make the patch work, the mask term wants none of them — and the sweep over 0.0001, 0.002, 0.01, 0.05 is the trade-off, one point per weight.

anneal #

{"start": 1.0, "end": 0.05} sets T on the first update and on the last, and the updates between get a geometric interpolation. The point is that σ(θ/T) approaches the step function [θ > 0] as T falls, so the soft mask the optimizer differentiates ends up close to the hard mask the score uses. This document has 20 updates — 20 epochs of one minibatch, because the training split is smaller than pairs: 16:

update15101520
T1.0000.5320.2420.1100.050

The eval pass at the end of each epoch runs with training cleared, so every held-out number on this page is of a hard mask, whatever T was.

A fit is not a second engine. An update is an ordinary observation pass over one minibatch, and the only things that happen between updates are an optimizer step and — at the end of an epoch — an eval pass on rows the fit never saw. params is the whole of the trainability declaration: the model is frozen and nothing else in the run carries a gradient.

Reading the mask #

A weights step publishes the fitted parameter as a result, and the save writes it as a safetensors bundle holding one slot, weight, with the featurizer's identity stamped in the header. For a gate that slot is θ, and the mask is θ > 0:

$ python mask.py
out/dbm/objective=0.0001/mask.safetensors 4 of 16 kept
out/dbm/objective=0.002/mask.safetensors 2 of 16 kept
out/dbm/objective=0.01/mask.safetensors 1 of 16 kept
out/dbm/objective=0.05/mask.safetensors 0 of 16 kept

Four, two, one, none — the same four numbers documents/v2/dbm.json's header records from 2026-09-21, from the same seed. That is the curve the sweep exists to draw: turn up the L1 weight and the fit keeps fewer units.

L1 weightunits kept, of 16
0.0001 4
0.002 2
0.01 1
0.05 0

The bars are the fraction of the 16 units whose θ came out positive, measured from zero.

How to read the result — and this one #

A mask fit has two numbers, and both are needed. The size of the mask is what the sweep moves. The held-out score is whether a mask that small still carries the answer. A sparsity curve is only worth reading against the score beside it:

L1 weightunits keptheld-out margintrain cross entropy
0.00014+0.2250 / −0.227710.4639 / 10.4677
0.0022+0.2259 / −0.226810.4635 / 10.4685
0.011+0.2249 / −0.227710.4638 / 10.4691
0.050+0.2239 / −0.228810.4648 / 10.4694

Both splits have two rows, so each cell is both of them — held_out_iia.json and ce.json, row by row.

this fit never separated anything

Read the middle column down. Keeping four units and keeping none give held-out margins that differ by about 0.001 on a scale where the two rows sit at ±0.22. That is not a mask that got sparser without losing anything — it is a metric that never distinguished the mask from nothing at all.

At an L1 weight of 0.05 the mask is empty, and an empty gate is the identity: m ⊙ f + (1 − m) ⊙ x with m = 0 returns x. That row is the unpatched model, and the other three are within a thousandth of it. The model has random weights and a 16-wide stream; it does not do the weekday task, so no subset of its units carries the answer and there was nothing for the fit to find.

The run is still doing what it says — the sparsity curve is real, and it is reproducible from the seed. What it is not is evidence about a model. Before believing a DBM result, check that the held-out score of the fitted mask is far from the score of an empty one, and that the model does the task at all. documents/real/weekdays_behavior.json is what that check looks like as a document.

The bundle #

Each point's mask.safetensors carries a header saying what the mask is of, and a later document that loads it is checked against that header key by key — model, revision, dtype, component, layer, kind, d. A mask fitted at one layer loaded at another would run, and would be nonsense, so it is refused naming the key that differs.

A gate nobody is fitting is always hard, including one loaded from a file. A loaded mask is a mask and nothing else: there is no temperature to set and no soft reading to fall into.
