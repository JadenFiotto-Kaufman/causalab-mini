Use case

Batching & remote

One document, three ways to run it: every row at once, eight rows at a time, and on a server that holds the weights.

Two flags change how a document runs without changing what it is. --batch-size N bounds how many rows one model call holds. --engine ndif moves the weights off this machine. Neither is part of the experiment, and the page below runs one document all three ways and compares the numbers value by value.

The document is documents/real/weekdays_layer_sweep.json — Llama-3.2-1B, fp32, 32 swept points of 42 rows with two metrics each, so 2688 numbers per run. Layer sweep is that document end to end; here it is here because it is big enough to run three times and compare.

The numbers #

local vs --engine ndif26882688097 / 97
local vs --batch-size 8268814275.9e-0565 / 97

Remote changed nothing. All 2688 values match to the bit, and every file the run wrote — 33 document.json and 64 metric tables — is byte for byte the same file. The serialization round trip, the block executing in another process, the plan being filled in from what came home: none of it perturbs the arithmetic.

Batching moved the last bits, and only of one metric. All 1344 iia values are identical — a match metric is an argmax, and the argmax does not move. 83 of 1344 logit_diff values are identical and the rest differ by at most 5.9e-05 on numbers around 2.4. Every point's mean is the same to four decimals, and the 65 byte-identical files are exactly the 33 document.json plus the 32 iia.json.

why a batch size changes anything at all

A matrix multiply over fewer rows reduces in a different order, and floating point addition is not associative. That is the whole mechanism. It is also why run.json records batch_size beside the library versions: it is not part of the experiment, and it moves the last bit of every number, so a result with no record of it cannot be compared with another.

--batch-size: what it bounds #

A window of rows is a whole small pass: the same forwards in the same order over a slice of the rows, with the values published before it sliced the same way, so a write still meets the operand of its own row. What the windows read is concatenated back in row order, and everything downstream sees one pass.

The windowing is in the shared walk, not in an engine. An engine is handed a forward that is merely shorter and cannot tell the difference — every per-row thing a forward holds is a tuple with one entry per row, so a window is a slice of each. Positions are absolute indices into the padded width the client fixed once for all rows, so they survive the slice unchanged.

With no --batch-size there is one window, which is the pass exactly as compiled: every row in one model call. On this document that is 42 rows of 8 tokens, and what it costs against the weights is small:

runpeak CUDA allocated
every row at once (42)4954 MiB
--batch-size 84783 MiB

171 MiB, on a document whose weights are about 4.6 GiB. Batching is not free — the two wall times above are the same to a tenth of a second and the arithmetic moves — so it is worth reaching for when the rows are what does not fit, and not before. The recorded run of weekdays_head_patching, 96 points over the same 42 rows, used --batch-size 16 (documents/real/README.md).

--engine ndif: what moves #

--engine ndif is not a different engine. It is the same NNterpEngine, built with dispatch=False so no weights are loaded on this machine, and executed with remote=True. The client holds a meta shell: enough of the model to resolve a component to a module path, to know a site's width, and to tokenize.

The whole plan runs inside one model.session(remote=True). A 32-point sweep is one job on the server, not 32 — the server log for the run above records one request, 4032 ms of execution inside the model actor, in a 9.5 s wall. The client's remaining time is building the meta shell, compiling 32 documents and tokenizing.

What comes home is plain: strings and tensors. The client already has the plan, so only what fills it in makes the trip, and the plan is filled in on arrival. That is why the output directory is identical rather than merely equivalent — the same writer writes it from the same plan either way.

Where the server is is nnsight's business, not mini's: NDIF_HOST overrides the configured base URL, and NDIF_API_KEY the key. There is no mini flag for either.

What run.json records #

Every output directory's root carries one. The three runs above, side by side:

Three fields differ, and the rest is the same because the same code ran:

fieldwhat it says
enginethe class. NNterpEngine for both local runs and for the remote one — ndif is a way of running that class, not another class
remotefalse locally, true through NDIF. This is the field that says where it ran
batch_sizenull for every row at once, 8 otherwise
versionstorch, transformers, nnsight, nnterp, pydantic — the packages whose code decides what a block does
causalab_minia sha256 over this package's own .py files. Two runs with the same digest ran the same code, whatever git says
served_dtypewhat the model's lm_head weight actually was, read inside the session
served_dtype is the answer to a question the document cannot ask

A document's model.dtype is a request. Locally it is honoured. On a server the deployment chose the dtype when it was deployed, dtype is not part of the model key, and a client cannot ask for one — so mini reads model.lm_head.weight.dtype inside the session and records what it got. The server used here serves fp32, which is why the numbers above are bit-identical rather than merely close.

a different deployment gives different numbers

The recorded run in documents/real/README.md went through an NDIF serving bf16 for the same fp32 document: the last-token sweep reads 0.86 there where fp32 reads 0.88, p_answer differs by up to 0.018, and L12 H28's logit difference is +0.051 against +0.054. Nothing about remote execution did that — the dtype did, and served_dtype is where the output directory says so.

the versions are the client's

provenance.record reads importlib.metadata where the CLI runs. On a remote run the block executes against the server's installed nnsight, nnterp and causalab_mini, and run.json has no evidence about those. It is a true record of what was asked for and an assumption about what ran it.

Wall times #

runwallwhat is in it
--device-map cuda16.2 smodel load, compile, 64 forwards
--device-map cuda --batch-size 816.2 sthe same, in 6 windows per pass
--engine ndif9.5 sno model load; 4.0 s of it server-side

The remote run is faster here because the replica is already hot and the client never loads 4.6 GiB of weights. That is the comparison NDIF is for, and it is the one the recorded numbers show too — documents/real/README.md records 8 / 12 / 33 / 61 s locally on an A100 for its four documents against 7 / 8 / 19 / 36 s through NDIF, each document one job.

what is not on this page

The server used here is a self-hosted NDIF on the same machine, with auth off and the document's own checkpoint pinned. A public server adds a queue, an API key, a network, and a deployment set you do not control — including its dtype.
