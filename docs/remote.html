Remote & NDIF

The same document with no local weights: --engine ndif, and what changes.

--engine ndif changes one thing in the run: the one model.session(...) is opened with remote=True. The client still compiles the document — the widths, the module paths, an interior's operation, the token ids of every prompt and every metric column — against a meta-device shell with no weights in it. What comes out is a plan of strings, integers and tuples, and that is what travels. The server runs the block on the checkpoint it already has loaded, against its own installed copy of causalab_mini, and only what fills the plan in comes home.

At a glance #

$ NDIF_HOST=http://localhost:8001 causalab-mini run documents/v2/entity_patch.json --engine ndif --out out/entity-ndif
✓ [ae1d1705ad59466198dcd56bb1b92c9a] COMPLETED    (0.4s) Your job has been completed.
out/entity-ndif/document.json
out/entity-ndif/run.json
out/entity-ndif/iia.json
out/entity-ndif/logit_diff.json

The same four files a local run writes, with the same bytes in the two metric tables. In run.json exactly one field differs, and it is remote.

how the blocks on this page were produced

The server this page talks to has causalab_mini and nnterp installed, so the block imports them rather than carrying them. execute also calls nnsight.register("causalab_mini") when remote is set (engine/engines/nnterp/engine.py:86), which ships the package's source instead; PR #1 deletes that line, and this page describes the world without it. The blocks that show which copy ran — the payload sizes and the server-side traceback — were produced with that one call rebound to a no-op from outside the checkout. Every number and every written file is byte-identical the other way; only the payload size and the file paths in a traceback are not.

What runs where #

--engine nnterp--engine ndif
weightsdispatched on this machinethe server's; the client holds a meta shell
the sessionsession(remote=False)session(remote=True)
--device-mappassed to the loaderignored — run only adds it when the engine is local
the tokenizer the block reachesthe loaded model'sthe served checkpoint's own
what compiles the documentthe same meta shell, on the client, either way

The tokenizer row is a rule, not an accident. A traced block ships every name it loads, so a block that closed over the client's tokenizer would carry that object to the server and resolve positions against it. The block reaches model.tokenizer instead — an attribute, and one of nnsight's persistent objects, which a server resolves to the served checkpoint's own. tests/test_structure.py reads the package's own source and fails if any trace body loads the bare name tokenizer, self, or a client-side module.

Pointing at a server #

mini has no host setting of its own. The host and the key are nnsight's, read from the environment at import:

variablewhat it does
NDIF_HOSTthe base URL of the API. Default https://api.ndif.us
NDIF_API_KEYthe key sent with every request. A server running without auth accepts anything, including nothing

Both can also live in $XDG_CONFIG_HOME/nnsight/config.yaml, which the environment overrides. What a server is serving, and at what dtype, is on its /status:

$ curl -s $NDIF_HOST/status | jq -r '.deployments[] | select(.deployment_level=="HOT") | [.repo_id, .dtype, .application_state] | @tsv'
hf-internal-testing/tiny-random-LlamaForCausalLM	float32	RUNNING
meta-llama/Llama-3.2-1B	float32	RUNNING

That listing had 553 entries; the other 551 are COLD, and a COLD record carries no dtype, because nothing has been loaded to have one. A document's model.key and model.revision have to match a record here, and its dtype is a request the server is free to ignore — see below.

The server needs the same packages #

A remote block is recompiled on the server and the modules it names are imported there. So the server must have causalab_mini and nnterp installed, at the versions the client has. /env says what it has:

$ curl -s $NDIF_HOST/env | jq -r '.python_version, (.packages | {torch, transformers, nnsight, nnterp, causalab_mini, pydantic} | to_entries[] | "\(.key) \(.value)")'
3.12.14 (main, Sep  1 2026, 00:10:07) [GCC 14.2.0]
torch 2.14.0+cu126
transformers 5.17.0
nnsight 0.8.1.dev125+g524c33fc
nnterp 0.5.0.dev0+internalsaccessors
causalab_mini 0.0.1
pydantic 2.13.4

A version string is coarse for a package installed from a checkout, so the sharper check is mini's own digest — a sha256 over every .py file in the package, which run.json already records. Read from inside a remote block against this stack, the server's install and the client's agree:

SERVER /usr/local/lib/python3.12/site-packages/causalab_mini/__init__.py
SERVER_DIGEST 76c8c9d0c0d1f3e0b8e2eaeb09564107d1c0a70cb9e8b7d6cecab09fdc92d8a1
CLIENT_DIGEST 76c8c9d0c0d1f3e0b8e2eaeb09564107d1c0a70cb9e8b7d6cecab09fdc92d8a1
MATCH True

The __file__ on the first line is the other half of it: the server's path, not the client's, which is what says the module was imported rather than rebuilt from the request.

What a mismatch looks like #

Nothing checks the two sides against each other. A skew shows up as a missing name, at the moment the block reaches for it — here, a client calling a function its server's copy does not have:

nnsight.intervention.backends.remote.RemoteError: Traceback (most recent call last):
…
  File "/usr/local/lib/python3.12/site-packages/ndif/services/ray/deployments/modeling/nns.py", line 183, in execute_traced_block
    tracer.execute(tracer.info.code)
  File "[skewed:25] …/probe_versions.py", line 27, in skewed
    return steps.a_function_added_after_the_server_was_built()
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
AttributeError: module 'causalab_mini.engine.steps' has no attribute 'a_function_added_after_the_server_was_built'
a skew that changes a number is silent

A missing name is loud. A function whose body changed is not: the server runs its own, the run completes, and run.json does not show it — provenance.record reads every version and the code digest on the client. On this stack that is visible in a small way already: the run record says pydantic 2.13.5, which is the client's; the server has 2.13.4.

What the request weighs #

Measured with nnsight's own report (NNSIGHT_DEBUG=1 prints the payload and the result blob, both after compression), and with cloudpickle's by-value set read at serialize time:

requestoutback
entity_patch — 4 rows, one swap, two metrics5,069 B998 B
weekdays_layer_sweep — 32 experiments x 42 rows14,471 B7,746 B
entity_patch, with register("causalab_mini") left on69,085 B—

The third row is the package travelling with the request: 13.6x the first, and the same ~64 KB of source on every request whatever the document asks. A plan is cheap to ship because it is only strings, integers and tuples — an anchored position costs a handful of them, and the code that resolves it is on the server already.

The dtype is the server's #

A document's model.dtype is a request. The deployment decides what it serves, and dtype is not part of the model key, so a client cannot ask for one and cannot see what it got from the outside. The block therefore reads model.lm_head.weight.dtype on the server and brings the string home, where it lands in run.json as served_dtype.

It matters more than a rounding note. Recorded on this stack, the same 32-point sweep run locally in fp32 and through NDIF, 2,688 values per comparison:

deploymentmetricidenticalmax abs diff
NDIF default (bf16)iia1341 / 13441
logit_diff0 / 13440.231
ndif deploy … --dtype float32iia1344 / 13440
logit_diff1344 / 13440

So "close, not equal" is entirely the served dtype. At fp32 every one of the 2,688 numbers is bit-identical to the local GPU run: neither the serialization round trip nor running in someone else's process perturbs the arithmetic. The three iia flips under bf16 are all at layers 12–13 at the last token, the two points where the sweep crosses over and the argmax between the two answers is nearly tied.

documents/real/README.md records the same comparison against a bf16 deployment on an A100: last-token IIA 0.86 where local reads 0.88, p(answer) differing by up to 0.018, L12 H28 at +0.051 against +0.054 — and the DAS rank curve identical.

Ragged results come home too, not just tensors. An anchored document's positions record — each row's window, its decoded tokens and its reason code — and the per-row eligible mask are nested dicts of integers and strings, and they arrive with nothing lost and nothing reordered. documents/v2/entity_patch.json, whose position is {"index": -1, "scope": {"variable": "entity"}}, writes the same positions column locally and remotely.

The server-side figure is the model actor's own log line (prev_stage_ms between running and completed). The rest is the client: importing torch, building the meta shell, compiling 32 documents and tokenizing. That is why a remote run of a small document is not faster — the weights were never the slow part. The model was already HOT for both figures; a cold deployment adds its load time to the first request.

When the server refuses #

A document whose write has nothing to write on some row is refused at run time, because whether a row's entity text is in that row's prompt is not known until the prompt is tokenized. Locally that is a causalab_mini.plan.plan.PlanError. Through NDIF:

nnsight.intervention.backends.remote.RemoteError: Traceback (most recent call last):
…
  File "/usr/local/lib/python3.12/site-packages/ndif/services/ray/deployments/modeling/nns.py", line 183, in execute_traced_block
    tracer.execute(tracer.info.code)
  File "/home/localjadenfk/wd/causalab-mini/causalab_mini/engine/engines/nnterp/engine.py", line 96, in execute
    steps.run(engine, plan, batch_size=batch_size)
  File "/usr/local/lib/python3.12/site-packages/causalab_mini/engine/steps.py", line 76, in run
    run(engine, child, state.child() if isinstance(child, Plan) else state)
…
  File "/usr/local/lib/python3.12/site-packages/causalab_mini/engine/steps.py", line 478, in _writes_land
    raise PlanError(
causalab_mini.plan.plan.PlanError: write 'patch' has nothing to write on row(s) {1: 'alignment_missing'}. A read may skip a row; a write may not — writing nothing somewhere is not an intervention, and the row would score as if one had happened. `alignment_ambiguous` is a value that is in the prompt more than once, and scoping the anchor is what makes it one

Three things to read off it. The message survives whole, down to the trailing advice, and the server's traceback comes with it. The frames say which copy ran: every mini frame below the block is the image's site-packages, and the one client-path frame is the traced block itself, which nnsight registers under the client's filename so the traceback can show the offending line. And the server knew what it was — its own log says error_type=PlanError:

ERROR [ndif.modeling] model execution errored … request_id=b645c48f52574292a39b1764223b7b23
  api_key=local stage=running error_type=PlanError fatal=False exec_ms=21.31
the type does not survive

The client raises RemoteError, whose bases are Exception and nothing else, so except PlanError: on the client does not catch a refusal that came from a server. The text and the traceback are intact; the class is not. With causalab_mini installed on both sides the real class is importable on the client, so this is a gap rather than a limit — and the runs that most want the type are exactly the ones whose refusals are decided at run time.

The other refusal worth knowing is the hooks engine's: it raises rather than run remote, because a hook is a Python callable on a module object in this process and there is nothing to ship. Remote is the nnterp engine's. --engine hooks never sets it, so you meet this one only from Python.

remote="local" #

execute takes remote as bool | str and passes it straight to the session, so remote="local" is nnsight's local simulation of a remote run: the session is serialized exactly as it would be for a server, this project's modules are hidden, and it is deserialized against the persistent objects a server supplies — which is how model.tokenizer resolves to the served checkpoint's. It is not reachable from the command line; the tests use it, and it costs no server:

$ uv run pytest tests/test_patching.py::test_remote_local_runs_the_same_plan_and_gets_the_same_numbers \
    tests/test_ragged.py::test_a_text_anchor_resolves_the_same_way_through_the_serialized_path -q
..                                                                       [100%]
2 passed, 1 warning in 13.79s

What it pins is the way out: a block that closed over something it should not, an anchor that resolved against the wrong tokenizer, a plan carrying something unpicklable.

What it does not cover is everything that is a fact about the other machine. It does not serialize the way home, so nothing it does proves a result can come back. It has one Python, one nnsight and one install, so no version skew can appear. It runs at the dtype you loaded, on the device you loaded, and not inside NDIF's autocast region. The first runs against a real server found seven defects invisible to the suite for exactly these reasons — among them that a filled-in plan cannot be pickled home at all, which is why execute brings back a flat {step path: {name: tensor}} and fills in the plan the client never gave up, and that NDIF runs a request under autocast, which downcast half of a Cayley solve until featurizer math was pinned outside it.

Running your own server #

Two stages: NDIF's own image, then the three checkouts on top of it, so the server can import what a block names. From a checkout of ndif:

V=$(git describe --tags | sed -E 's/^v//; s/-([0-9]+)-g/.post\1+g/')
docker build -f docker/Dockerfile --build-arg TORCH_CUDA=cu126 --build-arg NDIF_VERSION="$V" -t ndif-local:base .

Stage two installs nnsight, nnterp and causalab_mini with --no-deps — every dependency is pinned in the base image, and letting pip resolve here pulls a different torch — and passes each version in, because setuptools-scm cannot see a git history in a build context:

FROM ndif-local:base
COPY nnsight/ /src/nnsight/
RUN SETUPTOOLS_SCM_PRETEND_VERSION_FOR_NNSIGHT="0.8.1.dev125+g524c33fc" \
    pip install --no-deps --force-reinstall /src/nnsight \
 && python -c "import nnsight._c.py_mount"
COPY nnterp/ /src/nnterp/
RUN SETUPTOOLS_SCM_PRETEND_VERSION_FOR_NNTERP="0.5.0.dev0+internalsaccessors" \
    pip install --no-deps /src/nnterp
COPY causalab_mini_src/ /src/causalab_mini/
RUN pip install --no-deps /src/causalab_mini
RUN python -c "import nnsight, nnterp, causalab_mini, causalab_mini.engine.steps"

Build the context with git archive out of each checkout, so the image is a function of three commits and nothing else. Then run it and deploy the checkpoints the documents name:

docker run -d --name ndif-mini --gpus all --shm-size 4g -p 8001:8001 -p 9000:9000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface -e HF_TOKEN="$(cat ~/.cache/huggingface/token)" \
  ndif-local:mini

docker exec ndif-mini ndif deploy meta-llama/Llama-3.2-1B \
  --revision 4e20de362430cd3b72f300e6b0f18e50e7166e08 --dtype float32 --pinned
two things that bite

TORCH_CUDA has to match the box's driver. This machine's is 555.42.02 (CUDA 12.5), so cu126; a cu130 build produces a server that reports cuda_memory_bytes: 0 and no error at all. And a server started without a Postgres URL has auth off, which means every request is trusted and runs in-process inside the model actor with trust_remote_code=True. That is fine on localhost and nowhere else.

The HOT set lives in the controller's memory, so docker start brings the stack back without the deployments; re-run ndif deploy. The import nnsight._c.py_mount check in stage two is deliberate: without the C extension .save() fails on the server with an error that names neither.

The public service #

https://api.ndif.us is the default host, and the same /env call says what it has:

$ curl -s https://api.ndif.us/env | jq -r '.python_version, (.packages | {nnsight, nnterp, causalab_mini, torch, transformers} | to_entries[] | "\(.key) \(.value)")'
3.12.14 (main, Aug 14 2026, 15:34:45) [Clang 22.1.3 ]
nnsight 0.7.0
nnterp 1.3.0
causalab_mini null
torch 2.6.0+cu126
transformers 5.8.0

null is the answer: mini is not installed there, so a document cannot run on the public service — the block names modules the server cannot import. The nnsight line is a second reason, since a block from a 0.8 client is not something a 0.7 server can run. Remote means a server you or your group control, which is what the numbers on this page were measured against.
